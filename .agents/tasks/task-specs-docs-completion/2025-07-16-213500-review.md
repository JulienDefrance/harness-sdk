# Full Strands Ruby SDK: specs, docs, and implementation scaffold

This change introduces the entire Strands Ruby SDK as a greenfield project inside `strands-rb/`. It includes the core library (models, tools, event loop, hooks, interventions, plugins, storage, session, memory, telemetry), RSpec specs for all major components, comprehensive documentation (CLAUDE.md, AGENTS.md, README, architecture guide, provider guides), and supporting project infrastructure (gemspec, Rakefile, RuboCop config). The scope is the full SDK — roughly 19,000 lines of new Ruby across 126 files.

**Watch for:** Specs cannot actually run in this environment (no `bundle install`), so correctness is verified only via `ruby -c` syntax checks — meaning structural issues in mocks or assertion logic won't surface until CI (confirmed). The MCP Client spec mocks internal method `#spawn` on the subject instance, creating a fragile coupling to implementation rather than interface (confirmed). Documentation references features and code paths that aren't yet implemented (S3 storage, Gemini/Mistral providers) without marking them as planned/future (confirmed).

## High-level view

The SDK follows a zero-external-dependency architecture: Agent orchestrates calls through an EventLoop::Cycle, delegating to Model providers for streaming and Tool executors for side effects, implementing SigV4 signing and SSE parsing in pure stdlib Ruby.

The three new spec files (Bedrock, Anthropic, MCP Client) follow the established pattern from the OpenAI and Ollama specs — `stub_http_streaming` / `stub_http_error` helpers, `collect_events` aggregator, and context-grouped scenarios. They're syntactically valid but the Bedrock spec forces `@use_sdk = false` via `instance_variable_set`, leaving the SDK-path entirely untested. The MCP Client spec stubs `#spawn` directly on the subject, coupling the test to implementation internals.

Documentation is thorough for a v0 SDK but optimistic — README says "Ruby >= 3.2.0" while design.md targets "Ruby 4.0.6", and several docs reference unimplemented providers (Gemini, LiteLLM, Mistral, SageMaker, Writer) without marking them as planned.

## Bedrock spec: single-chunk delivery and missing SDK path

The `stub_http_streaming` helper yields the entire response body in a single chunk to `read_body`. If the implementation splits on `\n` or event boundaries during chunked reads, this test wouldn't catch framing bugs where an event spans multiple chunks.

The SDK path is explicitly disabled:

```ruby
before do
  model.instance_variable_set(:@use_sdk, false)
end
```

The `Aws::BedrockRuntime::Client` integration has zero spec coverage. The implementation performs SDK detection in `#initialize` via a `require` rescued on `LoadError`, so the only path exercised is the pure-HTTP fallback.

## Anthropic spec: missing mid-stream error event

The spec doesn't test what happens when the Anthropic API yields an `error` event type mid-stream (which can occur on server errors during generation). If the implementation doesn't handle this event type, the stream would silently drop the error. Worth verifying whether `#stream` raises or propagates in this case.

## MCP Client spec: private-method stubbing

The stdio transport tests stub `IO.pipe` and mock `client.spawn` directly:

```ruby
allow(client).to receive(:spawn).and_return(12345)
```

The actual implementation method is `spawn_process` (private), which calls `spawn(@env, *cmd, ...)`. Stubbing the message on the subject means any rename or extraction of the spawn logic breaks the spec without testing actual behavior. The HTTP transport tests use the same `Net::HTTP.new` mocking pattern as model specs, which is more maintainable since it stubs at the dependency boundary.

## Documentation accuracy

README.md says "Ruby >= 3.2.0" in Requirements. The design.md header says "Target Ruby Version: 4.0.6" (Ruby 4.0.6 doesn't exist as of this writing — likely a typo for 3.4.0 or aspirational). This inconsistency will confuse contributors checking minimum version compatibility.

The README documents all four implemented providers (Bedrock, OpenAI, Anthropic, Ollama) accurately but the design.md module structure lists Gemini, LiteLLM, LlamaCpp, Mistral, SageMaker, and Writer as if implemented. The tasks.md checklist is the authoritative source showing these are unchecked items.
